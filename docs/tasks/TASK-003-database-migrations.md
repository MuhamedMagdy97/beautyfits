# TASK-003 — Database Connection & Migration Foundation

## Goal
Make the database layer usable by every later task: migration commands, the first migration, a shared transaction helper, and integration tests that run against a real PostgreSQL database.

## Dependencies
TASK-002, TASK-002A (DB design and API contract approved v1.2).

## Source of Truth
- `AGENTS.md`
- `docs/database/database-design.md` §1, §23, §25, "v1.2 TASK-002A Amendments" (Reliability: `idempotency_keys`, `outbox_events`)
- `docs/architecture/system-architecture.md` §10, §11, "v1.2 TASK-002A Additions"
- `docs/testing/test-strategy.md` §4
- `docs/decisions/ADR-0003-database-access-and-migrations.md`

## Scope
- ID generation decision (ADR-0010): UUIDv7 generated by the Prisma client, stored as PostgreSQL `uuid`.
- First migration `shared_kernel`: the two shared-kernel tables approved in DB design v1.2 — `idempotency_keys` and `outbox_events`. No business tables.
- Migration scripts: `db:migrate`, `db:deploy`, `db:status`, `db:reset`.
- Transaction helper `runInTransaction` (`src/server/db/transaction.ts`): isolation level, timeouts, and retry of serialization conflicts.
- Integration test harness: separate Vitest config, a dedicated test database recreated from migrations on every run, table reset between tests.
- Documentation: ADR-0010, README, test strategy, AGENTS required checks, DB design §25.

## Non-Goals
- Business tables (identity, catalog, …) — owned by their feature tasks.
- Idempotency and outbox **services** (reading/writing logic, worker) — built by the first tasks that need them.
- Seeds (TASK-004), money/time helpers (TASK-005), CI (TASK-006).

## Database Changes
- New tables `idempotency_keys`, `outbox_events` and enums `idempotency_status`, `outbox_status`, exactly as in DB design v1.2 amendments.
- Unique `(scope, operation, key)` on `idempotency_keys`; index `(status, available_at)` on `outbox_events`.

## Security / Authorization
- The test database name must end in `_test`; the integration setup refuses to drop any other database.
- No secrets committed; `.env.example` contains local-only values.

## Acceptance Criteria
- [x] A clean database is created entirely from migrations (the integration setup drops and recreates the test database and applies all migrations on every run).
- [x] `runInTransaction` commits all writes together or rolls all of them back (integration-tested).
- [x] Serialization conflicts are retried only when retries are requested (unit-tested).
- [x] `npm run db:status` reports the migration state.
- [x] `npm run lint`, `npm run typecheck`, `npm test`, `npm run test:integration`, `npm run build` pass.

## Tests
- Unit: retry behaviour and option passing of `runInTransaction`.
- Integration (real PostgreSQL): migrations created both tables; commit persists; a thrown error rolls back writes to both tables; the idempotency unique constraint rejects a duplicate key; a failed transaction leaves earlier committed data untouched.

## Edge Cases
- Test database missing → created automatically. Test database left over from a previous run → dropped and recreated.
- `TEST_DATABASE_URL` missing or not ending in `_test` → integration run stops with a clear message.
