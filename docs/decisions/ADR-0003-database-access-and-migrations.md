# ADR-0003 — Database access (Prisma 7) and migration strategy

- **Status:** Accepted (TASK-002)
- **Date:** 2026-09-30
- **Relates to:** Database Design §1, §23, §25 ("ORM and migration tool"); Test Strategy §4

## Context

PostgreSQL is the single transactional source of truth. The database design requires integer minor-unit money, UUID ids, UTC timestamps, atomic multi-table transactions (checkout, reservations, wallet ledger), and concurrency-safe reservation (row locks or conditional updates). A clean database must be creatable entirely from migrations.

## Decision

**ORM: Prisma ORM 7.10.0** with the `prisma-client` generator and the `@prisma/adapter-pg` driver adapter.

- Generated client output: `src/generated/prisma` (gitignored, regenerated by `postinstall`).
- A single `PrismaClient` per process via `getDb()` in `src/server/db/client.ts`. It is created lazily, so the build does not need `DATABASE_URL`, and it is cached on `globalThis` for dev hot-reload.
- Transactions use interactive `$transaction` with explicit isolation where needed. Row locking (`SELECT … FOR UPDATE`) and conditional updates use `$queryRaw`/`$executeRaw` with tagged templates (parameterised, never string-concatenated). TASK-003 adds the shared transaction helper.
- `prisma.config.ts` holds the schema path, migrations path, and datasource URL. Prisma 7 no longer reads `.env` itself, so the config loads `.env` with Node's built-in `process.loadEnvFile` when present.

Why Prisma: it was the owner's pre-selected ORM. It supports every requirement above (transactions, raw SQL for locking, typed client, SQL migrations). Prisma 7 removed the Rust query engine in favour of a TypeScript client plus driver adapter, which simplifies deployment. Drizzle was the main alternative, and nothing in the requirements justified switching.

**Migration strategy: Prisma Migrate, SQL migrations committed to Git.**

- Development: `npx prisma migrate dev --name <change>` creates a reviewed SQL migration in `prisma/migrations/`.
- CI, staging, and production: `npx prisma migrate deploy` only. `prisma db push` is never used against shared databases.
- Migrations are forward-only. Destructive changes to historical business tables follow the no-hard-delete rule (AGENTS.md).
- Constraints that Prisma cannot express (partial unique indexes, CHECK constraints, append-only triggers for `audit_logs`) are hand-edited into the generated SQL migration.
- TASK-003 creates the first migration and adds `package.json` scripts for migrate/status. TASK-002 adds no tables.

**Seed strategy (TASK-004):** deterministic seed scripts wired through `migrations.seed` in `prisma.config.ts`, with production bootstrap (permissions, roles, settings, owner bootstrap) kept separate from development sample data.

**Schema conventions** (for all later tasks):

- Money: `BigInt` (or `Int` only where the range is provably small) minor units plus a currency; never `Float`/`Decimal` for stored money (R5, R9).
- IDs: UUID (`@db.Uuid`). The exact generator (v4 vs v7) is decided in TASK-003 (DB Design §25).
- Timestamps: `DateTime` stored as `timestamptz` in UTC.
- Table/column names: `snake_case` via `@@map`/`@map`, matching `docs/database/database-design.md`.

## Consequences

- `DATABASE_URL` is required at runtime and for migration commands, but not for `npm install`, lint, typecheck, unit tests, or build.
- The readiness endpoint (`/api/v1/health/ready`) pings the database with `SELECT 1`.
- A local PostgreSQL is provided by `docker-compose.yml` (development only).
